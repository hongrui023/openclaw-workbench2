## 五个角色的边界

| 角色 | 位置 | 运行期是否在链路里 |
|---|---|---|
| 开发助手 | 你的电脑 | ❌ 只在开发期出现 |
| GitHub 私有仓库 | 云端 | ✅ 只存代码与模板，**单向**分发，数据永不回流 |
| 工作台（本仓库） | NAS 容器 | ✅ 主角 |
| OpenClaw | NAS 内部 | ✅ 推理引擎 |
| 节点小宝 | 极空间系统服务 + 云端节点 | ✅ 唯一公网入口 |

三者之间全部通过标准接口解耦：把开发助手换成别的工具、把 GitHub 换成 Gitea、
把 AI 服务换成任何 OpenAI 兼容服务，项目照常运转。

## 一次"分析 ABC.pdf"的完整数据流

```
① 你在网页上勾选 ABC.pdf，点提交
        │  POST /api/literature/analyze  →  立刻返回 task_id（不等结果）
        ▼
② 后台任务 worker（单线程串行）
        │
        ├─ 路径守卫：literature/ABC.pdf 是否存在、是否在根内
        ├─ PyMuPDF 抽出全文（按页，带页码）
        ├─ 判断长度 → 直通模式 or 分段模式
        ▼
③ 适配层：把【纯文本】发给 AI 服务
        │  POST {base}/chat/completions   body 里只有字符串
        │  ★ 不传路径、不传文件名、不传任何凭据给模型
        ▼
④ 收到纯文本（Markdown）
        │
        ├─ 校验必备小节（缺了就判定失败，不写文件）
        ├─ 清洗（剥代码块、去 H1 标题、长度上限）
        ▼
⑤ 路径守卫：写入 literature/ABC.md
   ★ 文件名由工作台从用户输入的 "ABC.pdf" 推导，绝不来自模型输出
        │
        ▼
⑥ 追加一条任务日志到 life_notes/workbench_log.md
        │
        ▼
⑦ 网页每 30 秒轮询一次任务状态（响应约 150 字节）
   ★ 你可以在第 ① 步之后直接关掉浏览器，任务照跑
```

**关键点**：第 ③ 步那条线是**单向的纯文本通道**。
AI 服务从头到尾拿不到任何文件路径，它返回的文本也永远不会被当作文件名或命令使用。

## 长文献：分段 + 分层汇总

```
Level 0  PDF 全文
   │  按【页边界】切分（不是按字符数硬切，页码才能准确溯源）
   ▼
Level 1  N 个块 ──(逐块调用)──▶ N 份结构化要点
   │                              每份固定六类：背景 / 方法 / 结果 / 结论 / 局限 / 引用
   │                              每条要点带来源页码
   ▼
Level 2  若 N > REDUCE_FAN_IN
         ──(分组归并，默认 6 份一组，可多轮)──▶ 直到份数 ≤ 6
   │
   ▼
Level 3  最终 N' 份 ──(汇总调用)──▶ 完整六段式 Markdown，每节末尾标来源页码
```

**为什么每块要点要用固定结构**：只有各块输出同构，最终汇总才能规整地对齐到六个小节。

**成本**（一篇 50 页论文的粗估）：约 8 块 → 总调用约 11 次 → 耗时 4–12 分钟。
这就是"不截断"的代价。也是必须做异步任务的原因。

## 模块依赖方向

```
api/          路由层：只做参数校验、鉴权、调服务、组响应
  │
  ▼
services/     业务层：编排流程，不直接碰文件系统
  │  ├─ literature.py   文献分析编排
  │  ├─ notes.py        生活记录
  │  ├─ jobs.py         任务队列
  │  └─ openclaw.py ★   唯一的 AI 调用出口
  │
  ▼
security/     基础设施层
  ├─ paths.py  ★ 唯一的文件操作通道
  ├─ auth.py     认证与限速
  └─ sanitize.py 日志脱敏
```

两条"唯一通道"是整个设计的支点：

- **`security/paths.py`** 是唯一碰文件的地方 → 审计"能不能越界"只需读一个文件
- **`services/openclaw.py`** 是唯一对外发请求的地方 → 审计"发了什么"只需读一个文件

## 技术栈与取舍

| 层 | 选型 | 为什么 |
|---|---|---|
| 运行时 | Python 3.12 | PDF 解析生态最好；ARM64 轮子齐全；无编译步骤 |
| Web 框架 | FastAPI + Uvicorn | 自带参数校验与依赖注入（鉴权挂在依赖上，不容易漏） |
| PDF | PyMuPDF | 快、可靠、能按页取文本；有 manylinux aarch64 轮子 |
| 前端 | 原生 HTML/CSS/JS | 零构建、零依赖。约 30 KB，gzip 后 8–10 KB |
| 存储 | 文件系统（Markdown） | 数据形态就是文本追加，文件系统本身就是状态表 |
| 任务队列 | 进程内 asyncio + 单 worker | 4GB 内存；串行本来也是资源约束要求的 |
| 认证 | 标准库 `hashlib.scrypt` + `secrets` | 零额外依赖，无编译风险 |
| 基础镜像 | `python:3.12-slim`（Debian） | PyMuPDF 在 musl（alpine）下容易出运行时问题 |

**明确否决**：Vue/React 与构建链、数据库、Redis、Celery、n8n/Dify/FastGPT、
WebSocket、SSE。理由都是同一条：**为一个两功能的工作台引入这些，收益为零**。

### 为什么轮询而不是 SSE / WebSocket

穿透网关（反向代理）可能缓冲响应、按超时切断长连接。
**短轮询对代理最友好，兼容性最好**，而且天然支持"关掉页面任务照跑"。
代价是每 30 秒一个约 150 字节的请求——按最坏情况（全程走中转）算，
一次 8 分钟的分析约 16 次轮询，共约 10 KB。
